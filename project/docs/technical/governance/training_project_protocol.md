# 模型训练项目工程协议

状态：**现行工作约定**。本文定义目标和验收标准；除非代码和检查已提供证据，不表示现有实现已经满足。它不授权启动训练、获取数据或发布模型。安全与生命周期补充协议仍是草案；已存在的实验合同和门禁在迁移完成前继续有效；有冲突时先停止相关运行并明确裁决，不静默降低标准。

安全、合规、模型风险和生命周期控制详见[安全与生命周期控制补充协议](security_lifecycle_controls.md)；该补充协议同样是待确认草案，规定了 P0/P1/P2 门槛及现状边界。附件分析的 30 项处理方式见[逐项对照](issue_response_matrix.md)。

## 1. 目标与适用范围

本项目为单人开发，开发者兼任各项职责；以有记录的自查和自动化验证替代不适用的多人流程，但不得把自查称为独立审查，依法或高风险场景需要外部审核时须先取得。

项目长期目标是探索以可学习、可组合的基础神经元单元构建通用模型；研究假设、证据边界和验证路线见[研究方向](research_direction.md)。

本项目的核心工程约定是：**所有神经元共享一个模型架构和一份权重；每个神经元是该模型的一次独立运行**。神经元可持有各自状态，但暂不复制身份专属参数。共享算子直接更新节点向量不等同于执行模型化神经元。任意入度消息的聚合属于神经元模型自身，不设单独的可训练聚合模型。节点向量图结果只能作为路由/连接机制代理证据；若未来提出 untied per-neuron weights，须用参数、数据和计算预算匹配的对照证明收益。

本协议覆盖数据、模型、训练、评估、实验、检查点、发布和工程变更。研究代码可以探索，但对外报告的结果必须有可追溯证据。优先保证结果可信、行为可解释、资源可控，再考虑性能和规模；不预设特定的云平台或实验跟踪产品。

## 2. 分层与目录

- `src/newera/nlp_flow/`：可导入的领域实现和明确的内部接口。模型、数据、训练与评估逻辑不依赖具体命令行入口。
- `project/scripts/`：参数解析、组装依赖与调用领域模块的入口；入口不复制核心算法，不在导入时启动作业或访问外部资源。
- `project/configs/`：稳定命名、可审查的配置与实验契约；配置描述输入，不存放密钥、数据或运行状态。
- `project/tests/`：按被验证的领域组织；`project/docs/` 记录协议、设计、决策和使用说明。测试数据使用小型公开或合成样例。
- `.data/`、`outputs/`、`checkpoints/`：本地数据、运行产物和检查点；它们不作为源码提交，不把它们视为仓库开箱即有的内容。

正式目录最多 5 个直接子项；探索模块目录（`src/newera/nlp_flow/components/` 与 `src/newera/nlp_flow/model/`）超限仅告警，不阻断。文件和目录均计入，`__init__.py` 也计入；`.git`、`.venv`、构建产物、缓存和忽略的本地数据/输出不计入。根目录的 `uv.lock` 是标准 uv 项目锁文件，作为唯一工具元数据例外，不计入目录项数。先按职责聚合再拆分，名称体现功能，不用序号分组；禁止为凑数量制造无意义层级。新增模块须说明归属、依赖方向和入口，避免同一职责多处实现。已有目录数量检查作为基础门禁。

### 版本管理硬约束

- Git 是项目唯一的版本管理机制；本地只维护一个项目工作树和一个当前检出版本。切换历史状态使用 Git commit/branch/tag，不复制出 `project_v2/`、`backup/` 或 `final2/` 等目录。
- 项目内禁止用文件名或目录名保存版本迭代副本，包括 `_v2`、`-v3`、`validation_v10` 等形式。每项职责保留一个稳定、按功能命名的活动文件；历史差异由 Git 历史记录。
- 实验结果按稳定的任务名/run ID、数据指纹和运行清单标识，不通过复制 `config_vN.json` 或 `report_vN.md` 表示迭代。不可变实验记录可按 run ID 并存，但不能把它们包装成协议/源文件版本副本。
- `schema_version` 等运行时数据格式字段属于数据契约，不用于在项目文件树中并存多份源文件。
- `newera-gate` 检查仓库路径中的版本迭代命名；违反即失败。重命名配置时须同步更新唯一的消费者和文档引用。

## 3. 数据协议

每个数据版本必须记录来源及使用条件、采集时间、处理代码版本、过滤与去重规则、数据指纹、样本数和划分方法。划分依据应覆盖近重复、项目或来源等可能造成泄漏的边界；训练、验证、测试及基准集合的隔离检查必须有记录。

训练集用于拟合；验证集用于开发、调参和选择；测试集只在方案和选择规则冻结后用于最终报告。禁止使用测试集内容进行训练、模型选择或调试。发现污染或来源不明时，该数据和受影响的结果不得用于对外结论，先记录影响并重新划分或重跑。私有数据和敏感内容不得写入仓库或日志。

## 4. 实验与配置协议

按用途分层记录，避免研究模块的每次小修改都承担正式实验的完整流程：

- **本地探索**：允许快速修改、重跑和丢弃原型，不要求固定内部接口或逐次走发布流程。记录足以理解本次尝试的命令/配置、代码或改动、数据来源、种子（若有）、预算及关键结果；缺失时标明，不将其作为正式对比或能力证据。安全、数据隔离、资源上限和授权仍适用。
- **正式实验与对照**：使用唯一 `run_id`，在运行前确定并记录可解析配置、目标、数据版本、评估协议、随机种子、预算与停止条件；一次运行的记录固定后不得覆盖。迭代方案可创建新的运行，冻结针对该次实验，不冻结模块未来演进。
- **对外发布或生产使用**：在正式实验基础上执行发布、风险、兼容性及相关法规门禁；探索性结果不得冒充通过。

正式实验的运行记录至少包括：

| 类别 | 最低记录 |
| --- | --- |
| 身份 | 运行 ID、实验名称、状态、开始/结束时间、负责人或执行环境 |
| 代码与环境 | Git 提交、工作区是否干净及未提交补丁的可验证指纹、Python/PyTorch/CUDA 与关键依赖版本、硬件与设备数 |
| 输入 | 展开后的完整配置及指纹、数据版本/划分及指纹、初始化模型或检查点身份 |
| 过程 | 种子、精度、优化器与调度、全局 batch、梯度累积、资源预算、停止原因 |
| 输出 | 指标定义及数值、日志、检查点、评估报告、产物位置和完整性指纹 |

同一 `run_id` 不得覆盖已有运行；失败、取消、部分完成也必须有状态和原因。不能记录或核验关键身份时，结果标记为不可复现，不得与完整运行混为一谈。对比实验须先明确唯一变量、共同预算、种子和评估口径；预算不足或偏离计划要在结论中披露。

## 5. 训练、预检与资源

本地原型按变更风险选择必要的快速检查；正式训练在进入更高成本运行前，完成配置校验、数据与污染检查、小样本 CPU 前向/反向及适用的保存恢复检查。GPU 运行前记录设备、显存、驱动/依赖、预计时长和预算，检查设备是否空闲且获得所需独占资源；违反停止条件即停止并保存原因。分布式训练还须记录节点、设备映射、进程数、有效 batch、通信及失败行为。

种子和确定性选项必须记录；严格复现模式要求显式启用可用的确定性算法，并报告不支持的操作及性能代价。不同软件、硬件或执行方式不保证逐位一致，报告应区分逐位复现与容差内复现。

## 6. 检查点与恢复

可恢复检查点除模型参数外，应保存优化器、调度器、混合精度状态、训练步数、随机数状态、数据采样/迭代位置、配置与数据身份；分布式状态须能正确重建。加载前校验格式版本、完整性与兼容性，禁止静默部分加载。保存采用临时文件及完成标记/原子替换等适合存储后端的机制，避免将中断产物误判为完整检查点。

恢复测试需比较连续运行和中断恢复运行：验证步数、采样进度、优化器状态及指标在声明的确定性或数值容差内一致。只含推理权重的导出物必须明确标为不可恢复训练，不得冒充完整检查点。

## 7. 评估与发布

训练损失、代理指标、内部验证和正式基准分别记录，不得相互替代。评估前固定数据版本、提示/解码设置、执行环境、通过条件与聚合方式；同时报告失败、超时、缺失样本及样本数，不仅展示最优结果。外部代码执行须在单独受限的执行环境中进行；未具备隔离环境时不运行。

发布前按[模型卡模板](model_card_template.md)填写模型卡，至少具备模型/数据来源、训练配置、检查点身份、评估报告、限制与已知失败、复现步骤和许可证/使用条件。缺少必要证据时门禁发出警告而不阻断；状态仍为“研究中/未验证”，不作能力达标或生产可用声明，也不改变已有安全或训练专用门禁的行为。发布模型、写入外部服务和消耗计算资源仍按项目实际授权执行。

## 8. 工程质量与变更

实验性模块的内部结构、实现和接口可以快速演进或直接替换；不为内部原型强制向后兼容、稳定版本号、迁移层或额外审批。探索期间选择与风险相称的最小检查；变更涉及共享接口、训练/数据契约或发布产物时，记录影响并运行相关测试及适用的 CPU smoke。正式合并/发布前执行约定的格式、静态与相关测试，说明缺失项；对已有消费者或已发布的配置、检查点和输出格式，明确版本、兼容性与迁移方式。不因追求内部兼容而阻碍新方案，也不隐式篡改已有实验记录。

## 9. 落地顺序与当前边界

1. **P0：基线与协议确认**。确认本协议、训练目标和环境；补齐依赖后运行现有检查，建立可信基线。当前仓库不含数据、模型权重或隔离执行环境，完整测试与训练能力尚未验证。
2. **P1：可追溯运行**。实现并验证配置冻结、运行身份、环境与数据指纹、状态记录及统一产物清单；检查所有入口遵循同一协议。
3. **P2：可靠训练**。补齐 CPU 端到端 smoke、检查点完整保存/恢复及对照测试，再评估 GPU 和分布式支持。
4. **P3：可信评估与发布**。实现隔离与污染检查、固定评估报告、产物登记和模型说明；完成各门禁后再作相应声明。

每个阶段的交付都应有自动检查和可复核样例；未经验证的目标不得写成当前功能。
