# 安全、合规与模型生命周期控制（讨论稿 v0.3）

本文补充[模型训练项目工程协议](training_project_protocol.md)。优先级表示实施顺序，不代表本仓库已经具备这些能力。下列 CI、审查和版本门槛按[训练协议](training_project_protocol.md)区分本地探索、正式实验及对外发布，不要求内部原型每次迭代经过完整发布流程。本项目由一人开发，当前是本地研究代码快照，不含身份服务、在线推理服务、已登记的生产模型或经验证的持续交付系统；下列控制是**提议的门槛和验收要求**。本文件不构成法律意见，也不宣称符合任何法规。

## 适用方式和执行责任

- **本地离线研究**：适用密钥、数据来源与分类、依赖管理、审查和实验追踪；无对应服务时记录“不适用”和依据，不虚构监控或访问控制已部署。
- **共享环境或真实敏感数据**：先落实身份、授权、审计、保留和处置控制；未经授权不得导入个人或受限制数据。
- **外部发布或在线部署**：在上述基础上完成法规适用性、风险评估、隐私、公平性、安全测试、发布与回滚门禁。未满足的门禁阻止发布，不能以“研究性质”自动豁免。
- 由开发者兼任项目、数据、模型和运维责任人；不虚构第二名评审或独立审批人。用轻量记录登记适用对象、实现状态（未开始/进行中/已验证/不适用）、证据与复核日期。自查须记录测试结果、剩余风险和复核结论；自动检查和自查不能称为独立审计。
- 例外由开发者记录范围、原因、风险、替代控制和到期日，并在公开发布或处理敏感数据前复核；这属于自我风险接受，不声称独立批准。法律要求或高风险场景需要外部审核时，在取得审核前不开展相关活动；法律强制要求不得通过项目例外免除。

## P0：安全、合规与模型风险

### 1. 密钥管理

禁止将密钥、令牌、私钥、凭据放进代码、配置、测试样例、镜像、日志或实验产物。共享/生产环境使用受控密钥管理服务或平台原生短期凭据，限定用途和访问身份；本地开发使用受系统权限保护的注入方式。环境变量只是传递方式，并非保险库；禁止打印或持久化其值。

建立登记、最小权限、轮换、吊销和负责人制度；长期凭据建议每 90 天复核并按服务能力轮换（此周期为项目建议而非法定要求），短期凭据按有效期自动失效；凭据疑似泄露时立即撤销/轮换、保全证据并排查访问，而非只删除仓库中的文本。CI 对提交和历史范围执行密钥扫描，误报可审查豁免但不得记录真实密钥。验收：模拟泄露演练证明轮换后旧凭据失效、日志无密钥、未授权身份被拒绝。

### 2. 访问控制与审计

共享数据、模型、检查点、实验和部署环境必须使用具名身份及最小权限；单人开发不虚构职责分离，在确有需要时用隔离的个人和自动化身份降低权限；管理操作使用多因素认证，服务身份使用短期权限。禁止共享个人账号。授权定期复核，人员离开或权限变更时及时撤销。

记录登录、授权变更、敏感数据访问、密钥使用、模型/检查点导出、发布和删除等事件，至少包含主体、动作、对象、时间、结果和关联 ID；时间使用 UTC。日志不得包含凭据、原始敏感数据或完整提示内容。审计记录应受访问限制、具备防篡改和保留/删除策略；配置告警、定期复核与事件响应。验收：验证授权/拒绝、撤权后失效，以及关键操作的可追踪性和日志脱敏。

### 3. 法规与隐私

开始处理个人数据、面向特定地区提供服务或发布模型前，由负责人确认涉及地区、主体角色、用途、个人数据类别和适用义务；按需获得法律/隐私专业审核。GDPR 是否适用取决于事实与地域范围，若适用，须确定处理目的与法律依据、最小化收集、透明告知、保留期限、数据主体权利处理、处理者及跨境传输安排，并按风险实施安全控制；按适用条件评估 DPIA、事故通知义务和时限。数据主体删除请求应有登记、评估、执行或拒绝依据及反馈流程；涉及模型权重的影响需单独评估，不能承诺必然可从已训练模型中精确删除。

对欧盟 AI Act，按最新版法规评估是否适用、参与者角色、系统用途/风险类别、通用目的模型义务、例外和分阶段生效条款，形成有日期的适用性记录及证据矩阵；不假定所有本地研究或所有开源项目均受同一义务约束，也不假定普遍豁免。产品、市场或法规变化时重新评估。具备适用条件但尚未完成义务审查时，不向相关市场发布。中国境内处理个人信息或面向境内公众提供生成式人工智能服务时，还须评估《个人信息保护法》《生成式人工智能服务管理暂行办法》及数据跨境相关规定的适用范围；涉及加州消费者时评估 CCPA/CPRA 对主体、业务和活动的适用性。研究和线上发布的适用条件可能不同，不能只凭项目名称判断。

### 5. 偏见与公平性

面向用户的模型发布前，针对用途确定可能受影响群体、潜在损害与合法的数据采集方式；预先冻结评估集、子群和指标，并与总体结果一起报告样本量、置信区间/不确定性、缺失群体及局限。保护属性收集须有合法依据和最小化原则；样本不足时标注证据不足，禁止声称公平通过。

由开发者在评估前记录与风险相称的阈值、加权与例外处置；至少检查分组表现、错误率差异和适合任务的反事实样例。失败时记录、修复并重测；无法量化的危害记录人工评估与未覆盖范围。验收：评估报告、阈值、数据版本、复测结果和发布决策均可追溯。

### 6. 安全红队与对抗测试

发布前按用途建立威胁场景、攻击面和成功/失败判定，包括提示注入、越权工具调用、隐私泄露、训练数据记忆、恶意代码及越狱等适用项目；对受控合成数据或获得授权的环境执行。设置资源预算、隔离边界和停止条件，不对第三方系统发起未经授权测试。

固定测试集和版本，区分自动测试与人工红队，记录攻击、影响、严重度、缓解和复测；高严重度未缓解问题阻止发布。红队不是零风险证明。验收：开发者记录覆盖范围与剩余风险，所有阻断项已关闭或取消发布；独立审核只在法律或发布风险要求时作为额外门槛，未取得时不得声称已完成。

## P1：生命周期与工程门禁

### 4. 数据分类分级

默认分为公开、内部、受限、严格受限四级；个人数据、凭据、受合同限制的数据按风险取更高等级。按下表为每种数据和模型产物记录所有者、来源、用途、访问人群、存储、加密、传输、保留期限和删除方式；未知来源默认受限并隔离。定期复核，敏感级别不得因去标识化而自动降低。

| 等级 | 访问与存储 | 留存与销毁 |
| --- | --- | --- |
| 公开 | 可公开分发；校验来源及许可，维护完整性 | 按许可证和数据集生命周期决定；到期删除副本 |
| 内部 | 限开发者/明确授权身份；使用设备权限和加密存储 | 入库前记录期限；到期删除可控副本并记录 |
| 受限 | 最小权限；静态和传输加密；记录访问 | 按用途及适用规则确定期限，删除主副本并处理备份 |
| 严格受限 | 默认不接入；确有合法必要时先评估并启用隔离、强认证、加密和审计 | 在接入前确定最短期限、销毁和备份处置并留证 |

本表是项目拟议控制，不替代合同、法律或具体存储后端的要求。公开与内部也不得包含密钥；设备加密、云端加密和密钥管理需验证后才能标记已落实。

### 7–9. 版本、发布与监控

- **模型版本**：建议以 `MAJOR.MINOR.PATCH` 表达对下游契约的破坏性、兼容新增能力和兼容修复；权重、分词器、推理配置、数据、代码和评估的不可变指纹共同构成模型身份。版本号不能替代哈希，也不能保证能力或质量；预发布需显式标识。
- **发布与回滚**：登记候选版本、证据、发布审批、健康检查、流量策略、回滚触发条件和负责人。上线前至少保留当前版本及一个已验证可恢复的前一版本（首发无前版时制定停服/禁用方案），记录权重、分词器、配置和依赖指纹；发布前在受控环境演练恢复到已验证版本及依赖配置；数据/模式变更需单独定义可逆路径。回滚后验证服务、记录事件并复盘；没有可行回滚或替代处置不得上线。
- **上线监控**：上线前定义基线、可观测性、责任人、告警阈值、处置时限；监控可用性、延迟、错误、资源成本、安全事件、输入/预测分布和具备标签时的质量/子群表现。上线前确定监控数据留存时间；上线后建议每月至少复核一次和异常时即时复核，实际周期须记录并按风险调整。漂移告警需有样本量、窗口、统计方法、人工复核及抑制误报措施；缺少标签时不能把输入分布漂移当作性能下降证明。日志采样与留存应遵守隐私约束，禁止自动把线上输入加入训练集。

### 10–13. 评审、CI、依赖与覆盖

- **代码评审**：变更说明风险、关联需求、接口与配置影响、测试证据及回滚方案；合并前由开发者检查变更差异、测试证据和风险，安全、数据处理和训练/评估契约变更增加专项自查并留存记录；自查不等于独立审查。遇到法律要求或超出个人能力的高风险发布时，先取得外部专业审查，否则暂不发布。
- **CI/CD**：受保护分支禁止绕过必需检查；PR 至少执行格式/静态检查、相关单元及契约测试、密钥和依赖扫描、构建及目录约束。权限最小化、依赖及动作版本固定到可验证身份，隔离不可信贡献的执行环境；构建产物与代码提交关联。部署需单独授权，不能由不可信 PR 访问发布密钥。依赖数据或 GPU 的检查明确运行环境和未执行状态；不因缺少外部资源把缺失检查标记为通过。
- **依赖安全**：直接及传递依赖应可重建，生产/发布构建记录精确版本、来源、完整性校验和 SBOM；引入前评估维护状态、许可证和风险。持续扫描已知漏洞并分级处置；建议每月至少复核依赖、上线前扫描，已知可利用且涉及项目暴露面的严重问题立即隔离并在 24 小时内开始处置，高风险问题建议 7 天内修复或记录缓解与到期例外；这些是单人项目建议目标，具体取决于暴露面和可用补丁，不替代实际风险判断。禁止自动信任不明来源的模型权重、反序列化对象和安装脚本。
- **覆盖率提案**：先在可复现的 CI 中采集行与分支覆盖率基线并排除不可执行代码；建立基线后，建议新修改代码行覆盖率不低于 80%、分支覆盖率不低于 60%（可测量后另行确认），关键鉴权、数据隔离、恢复与发布门禁的正常及拒绝/失败分支均有测试。项目总体阈值基于实际基线经评审设定；在可比范围和覆盖工具不变时不得无说明降低已确认基线，不以数字替代有效断言。当前没有已验证的覆盖率基线或自动门禁，上述阈值尚待团队确认。

## P2：持续完善

1. **目录纪律**：正式目录最多 5 项；探索模块 `src/newera/nlp_flow/components/` 与 `src/newera/nlp_flow/model/` 超限只发警告。根目录标准锁文件 `uv.lock` 不计入目录项数。应以职责清晰和可导航为首要目标，工具和 CI 目录仍受正式目录约束。
2. **数据与组件许可证**：为每个数据源、模型权重、第三方库记录版本、来源、许可证、允许用途、限制、再分发条件和审核结论；来源或授权不明即隔离，不用于发布。数据访问凭据与许可证记录分离。
3. **成本与配额**：记录每次运行的设备时长、资源用量、预估与实际成本、预算上限和中止原因；在共享/云环境配置配额和告警，账单归属明确。
4. **文档同步**：接口、配置、数据契约、运行命令或门禁变更时，同一变更更新文档、示例和迁移说明；自动检查本地链接，定期清理过期文档。
5. **备份与恢复**：为关键元数据、登记记录和受许可保护的模型产物确定备份范围、加密、异地/隔离、副本保留、RPO/RTO 与责任人；定期执行恢复演练并记录结果。删除请求和备份保留政策需要协调。
6. **日志规范**：结构化记录时间、级别、组件、run/request ID、事件与结果；统一脱敏、访问与保留策略，避免输出密钥、原始个人数据和未经授权的训练样本。高风险事件可追溯但不过度采集。
7. **第三方组件**：评估来源、完整性、维护状态、许可证、漏洞和数据流；固定版本并提供替代或停用方案。联网下载和插件/远程代码执行需明确授权，下载产物校验身份与完整性。

## 对数据、运行与单人运维的补充要求（16–30）

### 数据管道与合成数据（15–18）

每个来源记录许可证名称或合同依据、许可证文本链接/受控存放位置、版本、商用与再分发限制、归属要求、许可证兼容性和审查结论；不明即隔离。每次预处理与增强记录源数据指纹、代码提交、依赖、操作顺序、参数、随机种子及输出指纹，必要时提供可重跑命令。

每批数据入训练前检查 schema、类型、必填字段、值域、重复与切分泄漏；可获得基线时检查分布变化并记录方法、样本量和阈值。失败则隔离批次并阻止训练，修复或记录针对具体批次的风险处置；不存在持续管道时按批执行，无需部署常驻监控。

合成数据标注生成器版本、提示/规则、种子、来源与允许用途；抽样核验有效性、重复、偏见和泄漏。可合法取得真实参照时，对相应字段比较分布，PSI/JS 等方法仅在数据类型和样本量适用时使用并披露阈值；不能取得参照时记录该限制，禁止把合成测试表现当作真实分布泛化证据。

### 预算、资源与故障（19–21、25–27）

每次付费运行前记录币种、单价、预计 GPU/CPU 时数、估算费用、硬上限、超时上限和停止方式；结束后记录实际用量与费用或标注账单未出。告警与中止阈值在启动前确定；超限先停止或安全暂停，再由开发者记录是否调整预算。若平台无法实现可靠自动中止，须先验证人工停止与账单告警，不能将其描述为自动保障。

采集可用的设备利用率、显存、存储和作业心跳；对可释放的云实例设置经验证的空闲回收策略，并在回收前保护运行和检查点。本地设备不适用云实例回收；空闲阈值按任务设定，避免因数据加载或检查点评估暂时空闲而误杀。

按资产记录备份目标、加密、保留期限、RPO/RTO、恢复命令和最近演练结果；关键检查点在适用条件下备份到独立故障域。训练数据只有在许可允许时复制，敏感数据和删除请求须覆盖备份处置。每次重要训练前确认可恢复的配置、数据标识和检查点。

对存储、跟踪、设备或网络中断，先停止写入并保留故障证据；检查产物完整性，从已验证检查点恢复。仅当数据版本与权限可验证时才使用本地缓存；不能安全恢复时失败退出，不静默切换数据或继续训练。单人开发以事件记录和必要时通知受影响方替代团队值班流程。

运行日志推荐 JSON 行，至少包含 UTC 时间、级别、组件、run_id、事件与结果；安全事件另加主体和对象标识。记录采集、保留、脱敏、访问权限、归档及删除方式，敏感信息不入日志。集中日志仅在确有远程部署时考虑，不是本地开发的先决条件。

### 评审、知识与交付（10–13、22–24、28–30）

单人开发每次合并前完成差异自查：接口/兼容性、数据安全、依赖许可、计算成本、失败路径、相关测试与文档同步；记录结论及未执行项。先建立 CI 基线，再设置有证据的阻断条件；扫描发现高危问题时按可利用性和暴露面阻断或记录经复核的短期例外。分析提出的多人审批 SLA 和导师制不适用于单人现状，若有外部协作者再定义。

建立轻量失败记录：run_id、现象、根因或未知、影响、修复、验证和后续措施；定期回顾，避免重复实验。维护可复现的环境初始化、依赖、CPU smoke、可选 GPU 检查、数据前提及常见故障说明；新贡献者加入时再补充权限、任务和交接流程，不虚构导师。

模型公开发布必须填写[模型卡模板](model_card_template.md)，包含来源、权重身份、预期/禁用用途、数据和许可、评估、适用群体、偏见安全、资源、限制及已知故障。第三方模型、数据、库及 API 接入前记录来源、许可证、版本/哈希、权限、数据外发、风险、更新与停用方案；默认关闭未经审查的远程代码执行。

参考资料按版本或合并文本记录查阅日期；法规和市场变化时重新检查，建议至少每半年复查一次。ISO/IEC 42001 可作为进一步研究的管理体系参考，不宣称已经认证；外部标准是否适用取决于用途和组织义务。

## 证据与实施顺序

P0 先建立责任人、适用性记录、密钥与访问控制方案，以及公平性/红队发布门槛；敏感数据处理、外部发布和生产上线分别在其相应门槛通过后进行。P1 在具备实际运行/部署环境后实施并测试版本、回滚、监控及 CI；P2 按风险和依赖持续完善。每项交付必须附证据和复核日期；文档本身不等于控制已生效。
